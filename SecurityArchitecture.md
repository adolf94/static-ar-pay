# Security Architecture: Verified QR Payments

This document outlines the security mechanisms implemented in the `ar-pay` application to protect against unauthorized modification of payment QR codes and account details.

## Overview

The application uses a **"Trust but Verify"** model. Payment data is fetched from a remote JSON file, but sensitive fields are only rendered if they are cryptographically signed by a trusted identity provider.

## 1. Cryptographic Identity (JWT)

Each bank account's data (Name, Account Number, QR Payload) is encapsulated within a **JSON Web Token (JWT)**.

*   **Header**: Specifies the algorithm (RS256) and Key ID.
*   **Payload**: Contains the `accountName`, `accountId`, and `qrData`. It also includes an `issuer` claim and an `exp` (expiry) claim.
*   **Signature**: Generated by the private key belonging to `auth.adolfrey.com`.

## 2. OIDC Trust Model (Verification)

The frontend application uses **OIDC Discovery** to verify tokens:

1.  **Discovery**: The app fetches `https://auth.adolfrey.com/api/.well-known/openid-configuration`.
2.  **Public Keys**: It retrieves the current public keys (JWKS) from the `jwks_uri` specified in the configuration.
3.  **Verification**: The `jose` library verifies that:
    *   The signature is valid for the provided public key.
    *   The token has not expired (`exp` claim).
    *   The token was issued by the expected authority (`iss` claim).

## 3. Verified-Only Mode (UI Defense)

To prevent "Silent Fallback" attacks (where a hacker removes a JWT to show unverified hardcoded data), the app implements **Verified-Only Mode**:

*   **Strict Adherence**: The `App.tsx` logic will **NOT** render the QR code or account details unless a `verifiedProvider` object exists (i.e., verification was successful).
*   **Fallback Protection**: Hardcoded data in `config.ts` is used **only** for non-sensitive UI elements like brand colors and logos. It is never used as a source for payment information.
*   **Security UI**: If verification fails or is missing, the UI displays a **"Secure Data Locked"** warning and disables the download functionality.

## 4. Threat Model & Mitigations

| Threat | Strategy | Mitigation |
| :--- | :--- | :--- |
| **Server Compromise** | Hacker modifies `accounts.json` on the web server. | **Signature Check**: The app will reject the modified file because the hacker lacks the private key to re-sign the tokens. |
| **Code Tampering** | Hacker adds `qrData` to the fallback `config.ts`. | **Verified-Only Logic**: The app explicitly ignores any `qrData` found in `config.ts` and only looks at the JWT payload. |
| **Man-in-the-Middle** | Hacker intercepts network traffic. | **HTTPS & HSTS**: All traffic to the OIDC provider and the app is encrypted. HSTS prevents downgrade attacks. |
| **Token Theft** | Hacker steals a valid JWT from the JSON file. | **Context Lock**: Tokens are specific to the issuer and account. While a token can be reused, it can't be modified by the hacker without breaking the signature. |

## Future Enhancements
*   **Content Security Policy (CSP)**: Implement a strict CSP to prevent XSS attacks that could bypass client-side verification.
*   **Subresource Integrity (SRI)**: Use SRI for any external scripts to ensure they haven't been tampered with.
